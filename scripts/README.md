# scripts — verifiche trasversali (docs/11 §10, docs/10 §11)

| Script | Cosa fa |
|---|---|
| `check-seed.mjs` | Valida i seed (docs/10 §11): JSON, espressioni di data, stringhe vietate, coerenza incrociata e, per ogni `seed/<file>.json` con un `seed/_schemas/<file>.schema.json`, conformità a quello schema JSON Schema 2020-12 (regola 1; `format` asserito, annotazioni `x-lh-*` ammesse; logica in `seed-schema.mjs`). Senza schemi gira senza dipendenze; con schemi serve `npm --prefix scripts ci --omit=dev`. Test: `node --test scripts/check-seed.test.mjs` |
| `vetrina-programma.mjs` | Configurazione di programma da `seed/` a un'installazione enterprise via API REST con il token di un operatore ADMIN (F2-DIST-09, F2-DIST-06, ADR-049, Q-617 default proposto, APERTA), senza dipendenze oltre a Node 22. Predefinito `--dry-run` (legge con GET e mostra il piano), `--apply` scrive, `--offline` mostra il piano dal solo seed senza rete né token. Crea solo ciò che manca (premi sempre in `DRAFT`, regola 22) e mai membri, movimenti, lotti, vincite, coupon, dati personali; le entità senza API di creazione (valute, livelli, tipi azione di sistema, mappature, edizioni) sono saltate e riportate (Q-629). Token solo da file `0600` (`--token-file`, `LH_OPERATOR_TOKEN_FILE`) o dal device flow (`--issuer`, `--client-id lh-cli`), mai stampato; `https` salvo `--allow-http` verso localhost; URL per servizio con `--base-url`, `--svc-url`, `LH_SVC_<SERVIZIO>_URL`. Dopo `--apply` verifica su `GET /v1/audit` una voce con attore reale per ogni scrittura (regola 21). Uscita 0 ok · 1 errore di lettura, scrittura o audit · 2 uso non valido. Uso e limiti: `deploy/README.md` («Vetrina enterprise»). Test: `node --test scripts/vetrina-programma.test.mjs` (hub finto in memoria, nessuna rete) |
| `check-contracts.mjs` | Job CI `contracts` (docs/05 §9, ADR-028, F2-EVT-01). Gate strutturale sui contratti eventi (envelope, schema per type, dataschema, audit con lhactor, `x-lh-pii`) e compatibilità di ogni schema con lo stesso file nell'ultimo tag `v<numero>` (`git describe --tags --abbrev=0 --match 'v[0-9]*'`) e nel merge-base col ramo base, senza dipendenze (logica in `contracts-compat.mjs`). Uso: `node scripts/check-contracts.mjs [--baseline=<ref>] [--base=<ref>] [--pr-labels=a,b]`. Bloccano schema rimosso o rinominato, `$id` cambiato, proprietà rimossa, campo reso o non più obbligatorio, restrizioni e cambi di tipo, schema chiuso o riaperto, `x-lh-pii` declassato, parole chiave che il confronto non interpreta (`oneOf`, `$ref`…) cambiate; passano schemi e versioni nuove e proprietà facoltative; gli allargamenti di valore (`enum` con un valore in più, vincoli tolti) sono solo segnalati (Q-541). Una rottura già presente nel merge-base non blocca di nuovo se la PR non la cambia ancora, e una PR non può rompere ciò che è già su `main` anche se il tag non lo conosceva (Q-542); con la label `decisione` sulla PR le rotture nuove sono riportate ma non bloccano (la label va messa all'apertura o prima di un push: il workflow `pull_request` non ha `types` e non si rilancia all'aggiunta della label, e un «Re-run» riusa l'evento originale; su una PR già rossa: label più commit vuoto). Senza tag `v<numero>`, o con un tag senza `contracts/events/` (oggi `v0.6.0`), si confronta solo col merge-base con un avviso (Q-540); senza nemmeno quello il confronto è saltato. Test: `node --test scripts/contracts-compat.test.mjs` |
| `wake.sh` | Risveglia i servizi serverless: interroga l'health finché tutti rispondono (timeout `TIMEOUT`, default 180 s). URL override con `BASE_<SERVIZIO>` |
| `smoke.sh` | Prova E2E del core loop: `POST /v1/events` (acquisto 130 €) → punti sul wallet entro 15 s. `MEMBER`, `AMOUNT`, `BASE_INGESTION`, `BASE_WALLET` configurabili. Invia come la fonte `ecommerce` (`X-LH-Actor: SOURCE:src-ecommerce`, Q-492); `SOURCE_CODE` sceglie un'altra fonte, `TOKEN` un access token del client `src-<codice>` (enterprise) |
| `check-adr-append-only.mjs` | Job CI `guard` (Fase 2, ADR-041): `node scripts/check-adr-append-only.mjs <base> <head> [--pr-labels=a,b]`; fallisce se una riga esistente di `docs/13` cambia o sparisce, o se un ID di `seed/` cambia senza la label `decisione` |
| `check-questions.mjs` | Job CI `guard` (ADR-047): `node scripts/check-questions.mjs [file]`; fallisce se un `Q-nnn` è definito più volte in `docs/15` (riga di tabella o punto elenco) e stampa il numero più alto in uso, da cui parte il prossimo blocco riservato |
| `check-api.mjs` | Job CI `contracts` (M8.8, docs/18 §3.6): `npm --prefix scripts ci --omit=dev` una volta, poi `node scripts/check-api.mjs [base-ref] [--pr-labels=a,b]`; confronta `contracts/api/*.openapi.yaml` con il merge-base del ramo base (default `origin/$GITHUB_BASE_REF` o `origin/main`) e fallisce sulle modifiche incompatibili. Test: `node --test scripts/check-api.test.mjs` |
| `check-mermaid.mjs` | Diagrammi Mermaid validi e con `accTitle`/`accDescr` (docs/18 §3.12): `npm --prefix scripts ci` una volta, poi `node scripts/check-mermaid.mjs docs site` (cartelle). Job `docs` da M8.9 |
| `docs-sync.mjs` | Pagine Mintlify generate da `docs/` (ADR-040, docs/18 §3.12), senza dipendenze. Oggi il backlog (M8.9b): `node scripts/docs-sync.mjs` rigenera `specifiche/backlog.mdx`, `specifiche/backlog/*.mdx` e il gruppo «Backlog» di `docs.json` da `docs/17` e dallo snapshot committato `specifiche/backlog/_status.json`, senza leggere altre evidenze. Le voci della Definition of Ready e della Definition of Done che dipendono dal testo della storia (R1–R4, D3) si calcolano a ogni esecuzione; quelle che dipendono dalle evidenze (R5–R8, D1, D2: `docs/14`, `docs/15`, `docs/testbook/`, sorgenti dei test, `seed/`, `.github/workflows/`) stanno nello snapshot, che `node scripts/docs-sync.mjs --refresh` riscrive insieme alle pagine nella PR di stato cumulativa (`docs(stato)`, ADR-047) e che registra SHA e data del commit di `HEAD`. `--check` (job `guard`) verifica solo la struttura: pagine, gruppo «Backlog» di `docs.json` e una voce di snapshot per ogni storia; non legge le evidenze, quindi una PR di codice non lo rompe. `--check-status` è un avviso: dice quante storie cambierebbero con `--refresh` ed esce sempre con 0. Rigenera le pagine dopo ogni modifica a `docs/17` (con `--refresh` se aggiungi o togli una storia). Test: `node --test scripts/docs-sync.test.mjs` |
| `check-helm.mjs` | Chart Helm e compose di riferimento (M8.3, F2-DIST-02/03): `node --test scripts/check-helm.mjs`, senza dipendenze. Copia del realm identica a `deploy/idp/realm.json`, ogni segnaposto `${LH_*}` passato a Keycloak, i 5 topic con i nomi di sempre, nessun segreto in chiaro, sicurezza `restricted` e risorse in ogni Pod; con `helm` nel PATH anche `helm lint --strict` e `helm template` |
| `security-iac.sh` | Job CI `security` (M8.11b, F2-SEC-03, ADR-042): `bash scripts/security-iac.sh`, con `trivy` e `helm` nel PATH (o `TRIVY`, `HELM`). Prova i controlli Compose del progetto (`.trivy/checks`) sulla fixture `.trivy/tests/compose-violazioni.yml`, rende il chart con `helm template` negli scenari del job `helm` e scansiona con Trivy `config` chart reso, `deploy/compose/reference.yml`, `deploy/docker-compose.yml` e `deploy/image/Dockerfile`; fallisce su HIGH e CRITICAL, salvo le eccezioni con scadenza di `.trivyignore.yaml` e `.trivy/ignore-policy.rego`. Dettagli in `docs/security/ci-security.md` |
| `security-dast.mjs` | Verifica dinamica notturna (M8.11c, F2-SEC-12, ADR-042): `npm --prefix scripts ci --omit=dev` una volta, poi `node scripts/security-dast.mjs prepare\|baseline-check\|fuzz-summary\|zap-gate` (dettagli in cima al file). Prepara le specifiche di `contracts/api` senza le esclusioni di `.dast/exclusions.json`, valida la baseline di Schemathesis e le eccezioni di ZAP (scadenza entro 90 giorni, motivo, `Q-nnn`/`TOBE-nnn`), riassume i rapporti e blocca sugli avvisi High non eccettuati. Test: `node --test scripts/security-dast.test.mjs` |
| `security-target.sh` | Bersaglio isolato del fuzzing e dello ZAP (M8.11c): `bash scripts/security-target.sh up\|down\|logs`. Kafka e Postgres del compose e l'hub (`LH_IMAGE`, default `lh-image:dast`) su una rete Docker interna, senza uscita; `up` prova l'isolamento e fallisce se da lì si raggiunge Internet. Richiede Docker |
| `security-fuzz.sh` | Schemathesis su ogni specifica di `contracts/api` (M8.11c): `bash scripts/security-fuzz.sh`. Docker con l'immagine fissata per digest, oppure `SCHEMATHESIS=<binario> LH_FUZZ_URL=<url>` in locale. `LH_FUZZ_OUT`, `LH_FUZZ_MAX_TIME`, `LH_FUZZ_BASELINE_UPDATE=1` per registrare i 5xx nella baseline. Blocca sui 5xx fuori baseline |
| `security-zap.sh` | ZAP API scan autenticato (M8.11c): `bash scripts/security-zap.sh` dopo `security-target.sh up`. Solo Docker, immagine fissata per digest. `LH_ZAP_OUT`, `LH_ZAP_MAX_MINUTES`, `LH_DAST_ACTOR`. Blocca sugli avvisi High non eccettuati |
| `setup-branch-protection.sh` | Ruleset `main-protetto` e impostazioni del repo (ADR-041): **solo il proprietario**, dopo il merge di M8.0; prima `--dry-run`; controlli obbligatori in `LH_REQUIRED_CHECKS` |
| `testbook.sh`, `testbook-report.mjs` | Esecuzione del testbook funzionale e rapporto riga per riga (docs/16 §1bis) |

Esecuzione locale completa (richiede Docker con accesso ai registri):

```bash
docker compose -f deploy/docker-compose.yml --profile all up --build   # stack + web
scripts/wake.sh        # attende che i servizi rispondano
scripts/smoke.sh       # azione → punti entro 15 s
```

(idem su 8082/8083/8084), oppure dalla Console demo del backoffice (BO-30).
