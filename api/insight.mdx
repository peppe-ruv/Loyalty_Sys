Il servizio Insight di Loyalty Hub e la finestra di osservabilita sulla piattaforma loyalty. Consuma tutti i topic Kafka, conserva gli eventi recenti, ricostruisce i tracciati end-to-end, calcola le metriche giornaliere ed espone audit, DLQ e un flusso live tramite SSE. E un servizio di sola lettura: non produce eventi Kafka (con un'unica eccezione, la rielaborazione DLQ che avviene via HTTP verso ingestion).

## Base URL

```text
http://localhost:8088
```

## Modello dati

Il servizio Insight persiste i dati in tre tabelle principali piu la DLQ.

- **event_store**
  - `event_id` (string): identificativo univoco dell'evento
  - `topic` (string): topic Kafka di origine
  - `family` (enum): `ACTION`, `EFFECT`, `FACT`, `AUDIT`, `DLQ`
  - `type` (string): tipo completo dell'evento
  - `short_type` (string): tipo abbreviato per la visualizzazione
  - `source` (string): sorgente che ha generato l'evento
  - `member_id` (string, nullable): identificativo del membro coinvolto
  - `correlation_id` (string): identificativo di correlazione del tracciato
  - `causation_id` (string): identificativo dell'evento causante
  - `hop` (int): numero di hop nel tracciato
  - `actor` (string): attore che ha generato l'evento
  - `event_time` (timestamp): istante di generazione dell'evento
  - `received_at` (timestamp): istante di ricezione da parte di Insight
  - `payload` (jsonb): corpo completo dell'evento
  - **Retention**: 14 giorni oppure 200.000 righe (la prima condizione che si verifica)
- **metric_daily**
  - `day` (date): giorno di riferimento
  - `metric` (string): nome della metrica
  - `dimension` (string): dimensione di raggruppamento
  - `dim_value` (string): valore della dimensione
  - `value` (decimal): valore numerico
  - `synthetic` (boolean): `true` se il dato e generato dal seed, `false` se reale
- **audit_entry**
  - `event_id` (string, UQ): identificativo univoco dell'evento di audit
  - `at` (timestamp): istante dell'azione
  - `actor_role` (string): ruolo dell'attore
  - `actor_name` (string): nome dell'attore
  - `service` (string): servizio che ha eseguito l'azione
  - `entity_type` (string): tipo di entita modificata
  - `entity_id` (string): identificativo dell'entita
  - `action` (string): azione eseguita
  - `summary` (string): riepilogo testuale
  - `before` (jsonb): stato precedente
  - `after` (jsonb): stato successivo
  - `correlation_id` (string): identificativo di correlazione
  - **Retention**: 180 giorni
- **dlq_entry**
  - `event_id` (string): identificativo dell'evento
  - `original_topic` (string): topic originale
  - `original_type` (string): tipo originale
  - `consumer` (string): consumer che ha fallito
  - `error_code` (string): codice di errore
  - `error_message` (string): messaggio di errore
  - `retryable` (boolean): se l'errore e ritentabile
  - `attempts` (int): numero di tentativi
  - `payload` (jsonb): payload originale
  - `status` (enum): `OPEN`, `REPROCESSED`, `DISCARDED`

## Stream live (SSE)

L'endpoint SSE trasmette gli eventi in tempo reale man mano che vengono consumati dai topic Kafka.

| Metodo | Path | Descrizione |
| --- | --- | --- |
| GET | `/v1/stream/events` | Stream live di eventi (text/event-stream) |

**Parametri query:**

| Parametro | Tipo | Descrizione |
| --- | --- | --- |
| `topics` | string | Filtro per topic, separati da virgola |
| `memberId` | string | Filtro per identificativo membro |
| `types` | string | Filtro per tipo evento, separati da virgola |
| `correlationId` | string | Filtro per tracciato |

**Formato evento SSE:**

```text
event: lh-event
data: {"eventId":"...","topic":"lh.actions.v1","family":"ACTION","shortType":"Purchase","memberId":"M123","correlationId":"corr-abc","time":"2024-01-15T10:30:00Z","summary":"Acqua minerale 1.50 EUR"}
```

**Caratteristiche:**

- Heartbeat ogni 15 secondi (evento `heartbeat`)
- Supporto `Last-Event-ID`: se specificato, il server rinvia fino a 200 eventi persi
- Content-Type: `text/event-stream`

**Esempio client JavaScript:**

```javascript Stream client SSE
const source = new EventSource(
  'http://localhost:8088/v1/stream/events?topics=lh.actions.v1,lh.effects.v1&memberId=M123'
);

source.addEventListener('lh-event', (e) => {
  const event = JSON.parse(e.data);
  console.log(`[${event.family}] ${event.shortType}: ${event.summary}`);
});

source.addEventListener('heartbeat', () => {
  console.log('heartbeat ricevuto');
});

source.onerror = (err) => {
  console.error('Errore SSE:', err);
};

// Riconnessione automatica con Last-Event-ID
// Il browser gestisce automaticamente l'header Last-Event-ID
```

> **Nota:** Il browser gestisce automaticamente la riconnessione e l'header `Last-Event-ID`. In un client Node.js o in ambienti server, devi gestire manualmente la riconnessione e inviare l'header `Last-Event-ID` per recuperare gli eventi persi.

### Rielabora evento DLQ

| Metodo | Path | Descrizione |
| --- | --- | --- |
| POST | `/v1/dlq/{id}/reprocess` | Rielabora un evento dalla DLQ |

**Comportamento:**

- L'evento viene reinviato al servizio ingestion tramite `POST /v1/events` mantenendo lo stesso `eventId`
- Se l'evento e un effetto o un fatto, restituisce `409 CONFLICT` con codice `NOT_REPROCESSABLE`
- Solo gli eventi di tipo azione possono essere rielaborati (ADR-002, eccezione 1)

> **Attenzione:** La rielaborazione e l'unico caso in cui Insight effettua una chiamata di scrittura (HTTP verso ingestion). In tutti gli altri casi, Insight e un servizio di sola lettura.

### Scarta evento DLQ

| Metodo | Path | Descrizione |
| --- | --- | --- |
| POST | `/v1/dlq/{id}/discard` | Marca l'evento come scartato |

**Body:**

```json Scarta evento
{
  "note": "Evento duplicato, gia processato manualmente"
}
```

> **Nota:** L'azione di scarto richiede il ruolo `ADMIN`. L'header `X-LH-Actor` deve corrispondere a un utente con ruolo amministrativo (es. `marta.admin`).

## Storico sintetico

Al seed, Insight genera 90 giorni di dati sintetici nella tabella `metric_daily` con `synthetic=true`. Questi dati simulano un carico realistico con le seguenti caratteristiche:

- **Stagionalita settimanale**: +35% di volume il sabato e la domenica
- **Rumore**: variazione casuale di ±12% rispetto alla media
- **Trend**: crescita giornaliera dello 0,4%
- **Picco**: un picco di traffico al giorno -30 (30 giorni prima del seed)

I dati reali si sommano ai dati sintetici. Nel backoffice (BO-01), i periodi sintetici sono marcati con un'indicazione visiva e una nota informativa.

> **Nota:** I dati sintetici sono utili per dimostrare le dashboard e le metriche in ambienti di sviluppo e demo. In produzione, i dati sintetici non vengono generati e le metriche si basano esclusivamente su eventi reali.

## Eventi Kafka

Il servizio Insight consuma tutti e cinque i topic Kafka (gruppo consumer `lh-insight`):

| Topic | Famiglia | Descrizione |
| --- | --- | --- |
| `lh.actions.v1` | `ACTION` | Azioni dei membri |
| `lh.effects.v1` | `EFFECT` | Effetti calcolati (punti, premi) |
| `lh.facts.v1` | `FACT` | Fatti di dominio (tier, stato) |
| `lh.audit.v1` | `AUDIT` | Audit delle modifiche backoffice |
| `lh.dlq.v1` | `DLQ` | Eventi finiti in dead letter queue |

Insight **non produce eventi Kafka**. L'unica eccezione e la rielaborazione DLQ, che avviene tramite chiamata HTTP al servizio ingestion (`POST /v1/events`) anziche tramite produzione diretta su Kafka.

> **Nota:** In futuro, il servizio Insight potrebbe essere sostituito o affiancato da un'architettura basata su ClickHouse per lo storage analitico e Apache Superset per le dashboard.
